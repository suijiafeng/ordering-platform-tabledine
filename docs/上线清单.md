# 上线清单（MVP）

> 按顺序勾选。第 1 节是外部前置条件；第 3 节起是工程动作。

## 1. 主体资质与域名

> 顾客端只有 H5（`customer-web`），会员余额支付：**不需要**注册小程序，也不需要微信支付商户号、支付宝签约与证书。

- [ ] 营业执照
- [ ] 域名已备案（ICP），解析到服务器（微信 / 支付宝内置浏览器打开未备案域名会被拦截）
- [ ] 若曾在微信 / 支付宝后台配置「扫普通链接二维码打开小程序」规则（前缀 `https://<域名>/q/`），**删除该规则**，否则扫码仍会进入已停用的小程序

## 2.（已停用）小程序平台配置

小程序 `miniapp/` 已移除，本节不再需要。日后如要重新启用微信 / 支付宝支付，见第 5 节与 git 历史中的旧版清单。

## 3. 服务器与部署

- [ ] 服务器安装 Docker + Docker Compose v2
- [ ] 后端镜像默认 `SPRING_PROFILES_ACTIVE=prod`；非 dev/test 环境下若模拟登录 / 模拟支付开启或使用开发密钥会**拒绝启动**（看 `docker compose logs backend`）
- [ ] `cp deploy/.env.example deploy/.env`，逐项填写：
  - `DB_PASSWORD`、`JWT_SECRET`（`openssl rand -base64 48`）
  - `QR_BASE_URL=https://<域名>/q/`、`PAY_NOTIFY_BASE_URL=https://<域名>`
  - 微信 / 支付宝相关参数（`WECHAT_*`、`ALIPAY_*`）会员余额模式下留空
  - `BOOTSTRAP_*`：首次启动创建门店与店主，成功后改回 `BOOTSTRAP_ENABLED=false`
- [ ] 替换 `deploy/nginx/conf.d/ordering.conf` 中的 `ordering.example.com`
- [ ] 首次签发 Let's Encrypt 证书（见 README「生产部署」第 4 步）
- [ ] `cd merchant-web && npm ci && npm run build`
- [ ] `cd customer-web && npm ci && STATIC_EXPORT=true npm run build`（产物 `out/` 挂载到 Nginx `/h5/`）
- [ ] `cd deploy && docker compose up -d --build`
- [ ] `docker compose ps` 全部 healthy；`curl https://<域名>/api/v1/c/stores/1` 返回店铺
- [ ] 用店主账号登录商家端，立刻修改初始密码（顶栏「修改密码」）
- [ ] 店铺设置：名称、营业时间、接单模式、三个超时参数
- [ ] 菜品、桌台录入；下载并张贴桌码

## 4. 顾客 H5 验证

- [ ] 手机浏览器打开 `https://<域名>/q/<桌码token>`：302 跳转到 `/h5/?token=…`，显示正确店铺与桌号
- [ ] 刷新 `/h5/order/?orderNo=…`、`/h5/orders/` 等深层页面不 404
- [ ] 分别用手机相机、微信扫一扫、支付宝扫一扫扫同一个桌码，都能在浏览器内打开点餐页
- [ ] iOS Safari、安卓 Chrome、微信 / 支付宝内置浏览器：底部购物车栏与安全区不遮挡，弹层能正常关闭

## 4a. 会员余额模式（主流程，不接微信 / 支付宝支付）

- [ ] 商家端「会员充值」开户一个测试会员，充值 0.10 元
- [ ] 手机扫桌码走一遍：浏览菜单 → 加购 → 提交订单时跳转登录 → 登录后回到确认订单页 → 「余额支付」→ 订单变为待接单，余额减少
- [ ] 余额不足时提交：提示「账户余额不足」，订单停留在待支付，余额不变
- [ ] 顾客取消待接单订单 / 商家拒单 / 店主退款：余额立即返还，会员页流水出现「退款返还」
- [ ] 店主重置会员密码 / 停用会员：该会员需重新登录 / 不能登录
- [ ] 看板「今日会员充值」与导出 CSV 中渠道显示「余额」

## 5. 支付渠道联调（仅当日后重新启用微信 / 支付宝支付时需要；会员余额模式见 4a）

> 先在商家端把一道菜改成 0.01 元专用于测试；跑完后下架。微信、支付宝各跑一遍。

| # | 用例 | 预期 |
|---|---|---|
| 1 | 用微信扫桌码 | 打开微信小程序，显示正确店铺与桌号 |
| 2 | 用支付宝扫同一个码 | 打开支付宝小程序，店铺桌号一致 |
| 3 | 用相机 / 其他 App 扫码 | 打开 `/q/{qrToken}` 匿名菜单，显示正确店铺与桌号，可分类浏览 / 搜索 / 查看规格，下单引导使用微信或支付宝小程序 |
| 4 | 商家端重置该桌码后再扫旧码 | 提示「桌码已失效」 |
| 5 | 商家端打烊后下单 | 可浏览菜单，提交订单被拒 |
| 6 | 下单 0.01 元并支付 | 拉起收银台 → 支付成功 → 订单详情显示「待商家接单」；商家端 5 秒内出现并有提示音 |
| 7 | 下单后取消支付 | 订单待支付，可在订单详情「继续支付」 |
| 8 | 待支付不付款等 15 分钟 | 自动关闭 |
| 9 | 待接单时顾客取消 | 自动退款，订单已取消，1 分钟内收到退款到账通知 |
| 10 | 商家接单 → 出餐 → 送达 | 顾客端状态同步（≤5 秒） |
| 11 | 制作中顾客申请退一道菜（0.01） | 商家端退款待审核 → 同意 → 退款成功，订单部分退款 |
| 12 | 商家拒单 | 自动全额退款 |
| 13 | 商家主动自定义金额退款（店主） | 成功；店员账号操作返回无权限 |
| 14 | 手动接单 10 分钟不接 | 自动取消并退款 |
| 15 | 流水导出当天 CSV | 订单与退款行金额与渠道对账单一致 |

- [ ] 核对微信支付商户平台 / 支付宝商家中心的交易与退款记录，与后端 `payment` / `refund` 表一致
- [ ] 查看后端日志无 `ERROR`（`docker compose logs backend | grep ERROR`）

## 7. 运维基线（上线当天完成）

- [ ] 数据库备份 cron：`docker compose exec -T postgres pg_dump -U $DB_USERNAME ordering | gzip > /backup/ordering-$(date +%F).sql.gz`，保留 7 天以上
- [ ] 探活：Uptime Kuma 或任意探活服务监控 `https://<域名>/api/v1/c/stores/1`
- [ ] 日志：`docker compose logs -f backend` 可查；退款失败、定时任务异常都以 `ERROR` / `WARN` 记录
- [ ] 商家端「退款管理 → 失败」每天看一次（退款失败需人工重试或线下退款）
- [ ] 证书：Let's Encrypt 自动续期，检查 certbot 容器在跑
