# 编码规范（短版）

> 原则：**读代码的人不用跳转就能看懂业务含义**。排版交给 `.editorconfig`；下面列出的是自动检查管不到、需要人工把关的部分。
> 自动检查：后端 `mvn verify`（Checkstyle，见 `server/checkstyle.xml`）；前端 `npm run lint`（ESLint）。CI 中违规即失败。

## 1. 调用处就能看懂

- 影响业务行为或信息可见性的参数，**不用布尔值 / `null` 表达**，改成两个方法或命名参数对象。
  - ✅ `assembler.customerDetail(order)` / `assembler.merchantDetail(order)`
  - ✅ `refundService.refundOrder(...)` / `refundService.refundExtraPayment(...)`
  - ❌ `assembler.detail(order, true)`、`fullRefund(order, null, ..., null, ...)`
- 反复出现的业务判断要命名：`category.isEnabled()`、`RefundStatus.isUnresolved()` / `isRefundUnresolved(status)`，不要散落 `status == 1`。
- 跨越多个业务步骤的变量不用缩写（`payChannel` 而不是 `pc`）；短小 lambda 里的单字母不受限。
- 金额、时长在**内部变量**名里带单位：`amountInCents`、`pollIntervalMs`。已有 API 字段不为此批量改名，在字段文档里写明单位（金额一律为分）。

## 2. 事务边界写在代码结构里（后端）

- 每个会改数据库的公开方法，在注释里写明它的事务边界，三选一：
  - **数据库事务**：`@Transactional`，被其他 Bean 调用
  - **事务提交后执行**：退款返还余额放在 `afterCommit`，在钱包自己的事务里执行；以后接入任何外部系统（支付、打印、通知）同样不在事务内等待
  - **独立新事务**：使用名字体现传播行为的模板，如 `requiresNewTx`
- 同类内部调用（`this.xxx()`）不会经过代理，`@Transactional` 不生效——需要事务时用 `TransactionTemplate` 显式开启，并在注释里说明原因。
- 不开启事务、只加入调用方事务的组件（如 `RefundLedger`），在类注释里写明。
- **调整事务边界必须补集成测试**覆盖：成功提交、执行出错（用 `@SpyBean` 注入故障）、并发重复请求三种情况。

## 3. 错误由谁负责

| 场景 | 谁提示 | 页面还要做什么 |
|---|---|---|
| 用户点击的操作 | 请求层（未传 `silent`） | `catch (e) { ignoreShownError(e) }`，恢复按钮、保留输入 |
| 页面首次加载 | 页面（展示错误态） | 提供重试入口 |
| 后台轮询 | 不弹提示（`silent: true`） | 展示数据是否过期 / 连接状态 |

- 不写空 `catch`。确实可以忽略时，用 `ignoreShownError(e)`（只吞请求层已处理的 `ApiError`，代码缺陷继续抛出）或写明忽略理由。
- 判断错误类型用 `instanceof ApiError`，不用 `as ApiError`（类型断言不做运行时检查）。
- Promise 必须 `await` / `return` / `.catch`，或用 `void` 明确表示有意不等待（ESLint `no-floating-promises`）。
- 后端：数据库约束异常按类型分级——输入超长 422、唯一冲突 409、业务不变量（CHECK 约束）500 并记录完整堆栈，绝不伪装成输入错误。

## 4. 职责划分

- **Controller**：参数校验、权限注解、调用一个 Service 方法。不写业务判断。
- **Service**：一个业务流程的编排与事务边界。超过一屏的纯计算抽到 `*Calculator`（无数据库读写，可直接单元测试）。
- **Mapper**：只做数据访问；条件更新（`WHERE status = ?`）是并发控制手段，写在 Service 里时注释为什么。
- 拆分的判断标准：这一部分是否有**独立职责**、是否值得单独理解和修改；不按行数拆。
- 前端页面：数据加载 / 轮询 / 生命周期抽成 Hook（如 `useOrderPolling`），页面保留操作入口与展示。

## 5. 注释

- 解释**为什么**（规则来源、并发 / 资金风险、和外部系统的约定），不逐行翻译代码。
- 业务规则变化时，同一次提交里检查并更新相关注释；失效注释比没有注释更有害。
- 历史修复过程留在提交记录里，代码旁只保留**当前成立的规则**。

## 6. 提交

- 纯格式 / 重命名与业务修改分开提交，便于审阅。
- 提交信息说明「改了什么、为什么」；涉及资金、事务、权限的改动注明对应的测试。
