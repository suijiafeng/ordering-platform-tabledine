# 项目架构

> 面向接手这个项目的人：先读这一篇，再按需要看 [README](../README.md)（本地开发）、[部署](../deploy/README.md)、[上线清单](上线清单.md)、[编码规范](编码规范.md)。
> 现状以本文和 README 为准；[工程化设计文档](点餐平台工程化设计文档.md) 是最初的设计，其中小程序相关章节已过时。

## 1. 这是什么

单店堂食扫码点餐。顾客用手机扫桌上的二维码，在浏览器里点餐，用会员余额支付；商家在后台接单、出餐、处理退款，并管理菜品、桌台、会员和员工。

没有微信 / 支付宝支付，也没有小程序：会员账号由商家开通，余额由店主线下收款后充值，所有资金只在本系统内流转。这让部署不需要任何第三方资质，也让支付没有回调、对账这些环节。

## 2. 组成部分

```
ordering-platform/
├── server/          后端 API：Spring Boot 3.3 + MyBatis-Plus + PostgreSQL 16 + Flyway
├── customer-web/    顾客端 H5：Next.js（静态导出）+ antd-mobile + zustand
├── merchant-web/    商家后台：Vite + React 18 + Ant Design 5 + zustand
├── deploy/          生产部署：docker-compose、Nginx 配置
└── docs/            文档
```

三者只通过 HTTP API 通信，所有业务逻辑都在后端；两个前端是纯静态产物，由 Nginx 直接提供。

### 运行时拓扑

```
手机 / 电脑浏览器
      │ HTTPS
      ▼
   Nginx（443）
   ├── /            → merchant-web 静态产物（商家后台）
   ├── /h5/         → customer-web 静态产物（顾客端）
   ├── /q/<token>   → 302 跳转到 /h5/?token=<token>（桌码链接，已张贴的二维码永远不用换）
   ├── /api/        → backend:8080
   └── /uploads/    → 菜品图片（Docker 卷）
      │
   backend（Spring Boot，启动时 Flyway 自动建表 / 升级）
      │
   postgres 16（Docker 卷）
```

另有一个 certbot 容器负责证书自动续期。

## 3. 核心业务流程

### 顾客点餐

1. 扫码进入 `/h5/?token=…`，前端调 `GET /api/v1/c/qr/{token}` 解析出门店和桌号，再拉 `GET /api/v1/c/stores/{id}/menu`。浏览菜单、加购物车都不需要登录，购物车保存在浏览器本地。
2. 提交订单时才要求登录会员账号（手机号 + 密码，`POST /api/v1/c/auth/password-login`）。
3. `POST /api/v1/c/orders` 下单：服务端按最新菜单重算价格、扣减每日限量库存；`clientRequestId` 保证重试不会重复下单。订单进入「待支付」。
4. `POST /api/v1/c/orders/{no}/pay` 余额支付：在同一个数据库事务里建支付单、扣余额、写流水、把订单转为「已支付」（店铺开了自动接单则直接「制作中」）。余额不足整个事务回滚，订单仍是待支付。
5. 顾客端订单详情每 5 秒轮询一次直到订单结束，可以取消（待接单前）、申请退款、撤回申请。

### 商家处理

商家后台每 5 秒轮询 `GET /api/v1/m/orders/new-count`，按「当前待接单订单号集合」判断是否有新单（不靠时间游标，不会漏）；有新单播放提示音并进消息中心。接单 → 出餐 → 送达的每一步都是订单状态机上的条件更新。

### 退款

退款单有自己的状态机：`APPLYING`（顾客申请，待审核）→ `PROCESSING` → `SUCCESS / FAILED`，另有 `REJECTED`、`WITHDRAWN`、`OFFLINE`（线下退款）。商家主动退款和系统自动退款（拒单、超时未接单）直接进入 `PROCESSING`。

返还余额发生在退款单事务提交之后：先锁住退款单行，确认它仍是 `PROCESSING`，再把钱退回会员余额。返还出错时退款单保持「处理中」，补偿任务每 5 分钟按钱包流水查询：已返还就回写成功，没有返还就用同一个退款单号重新提交（按单号幂等，不会重复退）。

### 定时任务（`module/task/OrderTasks`）

| 任务 | 频率 | 作用 |
|---|---|---|
| 超时关单 | 每分钟 | 待支付超过店铺设置时长的订单关闭并回补库存 |
| 超时未接单自动退款 | 每分钟 | 手动接单模式下，已支付超过时长未接单的订单取消并退款 |
| 退款补偿 | 每 5 分钟 | 处理中超过 3 分钟的退款按钱包流水查询并重试 |
| 待审核退款提醒 | 每 10 分钟 | 申请超过 2 小时未审核的记录告警 |
| 每日限量重置 | 每天 0 点（上海时区） | 把今日剩余重置为每日限量；下单前、拉菜单时也会幂等补做，停机错过 0 点不会漏 |

## 4. 后端结构

`server/src/main/java/com/example/ordering/`，按业务模块分包，每个模块是 `controller / service / mapper / entity / dto`：

| 模块 | 内容 |
|---|---|
| `auth` | 员工登录（账号密码 + refresh token）、会员登录与改密、登录失败锁定 |
| `menu` | 分类、菜品、规格组 / 加料组、上下架、沽清、每日限量 |
| `order` | 下单、订单状态机（`OrderStateService`）、顾客端与商家端订单接口、订单视图组装 |
| `pay` | 余额支付（`PayService`、`BalancePayChannel`）、支付单 |
| `wallet` | 会员钱包：充值、扣费、返还，每次变动写一条流水 |
| `refund` | 退款：流程编排（`RefundService`）、金额计算（`RefundCalculator`）、入账（`RefundLedger`）、视图（`RefundViewAssembler`） |
| `member` / `staff` / `store` / `table` | 会员、员工、店铺设置、桌台与桌码 |
| `report` | 看板、区间统计、CSV 导出 |
| `file` | 图片上传（校验、压缩、缩略图） |
| `task` | 定时任务 |

横切部分：

- `security`：双 JWT 体系。顾客 token（audience=customer）和员工 token（audience=merchant）互不通用；员工 token 带 `token_version`，会员 token 也带，停用、改密后旧 token 立即失效。
- `tenant`：商家端请求由 JWT 注入门店上下文，MyBatis-Plus 租户插件自动给 `staff / category / dish / dining_table / orders / refund` 加 `store_id` 条件。顾客端和定时任务没有门店上下文，代码里显式按 `store_id` 过滤。
- `ratelimit`：按客户端 IP 限流；只信任内网反向代理的 `X-Real-IP`。
- `common`：统一响应 `Result`、错误码 `ErrorCode`（HTTP 状态 + 业务码）、全局异常处理。
- `config/StartupSafetyCheck`：非 dev / test 环境下使用仓库里的开发密钥会拒绝启动。

接口前缀：`/api/v1/c/**` 是顾客端，`/api/v1/m/**` 是商家端。开发环境可在 `http://localhost:8080/swagger-ui.html` 查看。

### 数据模型

18 张表，全部由 Flyway 管理（`server/src/main/resources/db/migration`，当前到 V9）：

- 门店与人：`store`、`staff`、`customer`（会员：手机号、密码、余额、`token_version`）、`customer_auth`（已停用的小程序登录留下的历史数据）
- 菜单：`category`、`dish`、`dish_spec_group`、`dish_spec_item`、`addon_group`、`addon_item`、`dining_table`
- 交易：`orders`、`order_item`（下单时的价格与规格快照）、`order_status_log`、`payment`、`refund`、`refund_item`、`wallet_transaction`

## 5. 贯穿全局的约定

- **金额**全部是「分」的整数；前端只在输入和显示时换算成元。
- **状态变更都是条件更新**（`UPDATE … WHERE status = 原状态`），并发下只有一个赢家，不靠锁顺序。涉及金额校验的地方（建退款单、发起支付、返还余额）会先 `SELECT … FOR UPDATE` 锁住订单或退款单。
- **幂等键**：下单 `client_request_id`，支付 `out_trade_no`，退款 `refund_no`，充值 `request_id`；数据库唯一索引兜底。
- **会员只能在开户门店消费**，余额跨店不通用。
- **菜品规格按 id 同步**：编辑菜品时带回规格项 id，服务端原地更新，顾客购物车里已选的规格不会失效；删除的规格项软删除，历史订单用快照不受影响。
- **退款返还余额在事务提交后执行**；以后接入外部系统（打印、通知）同样不在事务内等待。
- **数据库变更只通过新增 Flyway 脚本**，不改已执行的脚本。

## 6. 前端结构

### customer-web（顾客端）

- `app/` 一个目录一个页面：菜单（首页）、`checkout` 确认订单、`login`、`order` 订单详情、`orders` 我的订单、`me` 我的账户。
- `components/`：购物车栏、规格弹层、退款弹层等；`hooks/useOrderPolling.ts` 负责订单详情的轮询与页面可见性。
- `lib/api.ts` 统一请求封装（注入 token、登录失效时跳转登录页并带回跳地址）；`store/ordering.ts` 用 zustand 持久化购物车，菜单刷新后自动对账。
- 部署在 `/h5`（`next.config.ts` 的 `basePath`），`STATIC_EXPORT=true npm run build` 产出 `out/`。

### merchant-web（商家后台）

- `pages/` 按功能分：订单、出餐看板、退款、菜品、桌台（含批量打印桌码）、会员充值、数据看板、员工、店铺设置。
- `api/` 与后端控制器一一对应；`hooks/useOrderPoll.ts` 是全局的新订单轮询和提示音；`store/` 放登录态、消息中心；`layouts/MainLayout.tsx` 是带侧栏、铃铛、主题切换的外框。
- 店主专属页面在路由上用 `RequireOwner` 守卫，后端同样用 `@PreAuthorize` 限制。

两个前端共同的错误处理约定：请求层统一提示错误，页面用 `ignoreShownError(e)` 只忽略已经提示过的错误，其他异常继续抛出。

## 7. 质量保障

- 后端：Checkstyle（`mvn verify` 时执行）+ 77 个测试。集成测试用 Testcontainers 启动真实 PostgreSQL，覆盖下单、支付、履约、退款全链路以及并发与故障场景（用 `@SpyBean` 注入返还出错、结果丢失等）。Docker 29 上需要 `mvn verify -DargLine="-Dapi.version=1.44"`。
- 前端：ESLint（规则只管正确性：Promise 必须处理、Hook 依赖、空 catch 要写理由等），`npm run lint` + 构建。
- CI（`.github/workflows/ci.yml`）对 server、merchant-web、customer-web 分别跑检查和构建。

## 8. 部署与运维要点

详细步骤见 [deploy/README.md](../deploy/README.md)。要点：

- 一台装了 Docker 的服务器即可；`deploy/.env` 只需要域名、邮箱、数据库密码、`JWT_SECRET` 和首次初始化的店主账号。
- 两个前端在 `deploy/nginx/Dockerfile` 里构建并打进 Nginx 镜像，后端镜像由 `server/Dockerfile` 构建；服务器上不需要 Node / Java。
- Nginx 配置是模板（`deploy/nginx/templates/`），启动时把 `${DOMAIN}` 替换成 `.env` 里的域名。
- 首次启动按 `BOOTSTRAP_*` 创建门店和店主，之后把 `BOOTSTRAP_ENABLED` 改回 `false`。
- 数据库备份、探活、日志查看见 [上线清单](上线清单.md) 第 7 节。
